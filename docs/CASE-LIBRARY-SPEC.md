# Case Library V1 — 案例库数据规范

> 状态：V1 骨架已就绪（2026-09-08）。50 个案例文件与数据索引已创建，**正文留空待 Copilot 分阶段导入**。
> 本文定义案例文件的字段与结构、导入工作流与站点行为，是案例内容导入的唯一依据。

## 一、文件位置

```
content/cases/
├─ Case-001.md  ~  Case-050.md   # 案例正文（Markdown 单文件）
└─ index.json                     # 数据索引（由脚本生成，勿手改）
```

- 每个案例一个文件，文件名即案例编号：`Case-001.md`。
- 站点运行时直接读取 Markdown 文件，**内容以 Markdown 文件为准**；`index.json` 仅作元数据索引与校验快照。

## 二、文件结构（11 个统一字段）

每个 `.md` 文件由两部分组成，对应 11 个字段：

### 1. Frontmatter（5 个元数据字段）

```yaml
---
id: Case-001          # 案例编号，与文件名一致
title: "一只基金的认购与接纳判断"   # 案例标题（导入后必填）
level: "进阶"          # 难度：入门 / 进阶 / 高级
category: "募集运营"    # 主题分类，建议复用课程地图归属词
tags:                 # 自由标签（筛选用）
  - investor
  - aml
---
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 案例编号，与文件名一致，勿改 |
| `title` | ✅ 导入后 | 一句话标题，目录卡片展示 |
| `level` | ✅ 导入后 | 难度（入门/进阶/高级），目录难度筛选用 |
| `category` | ✅ 导入后 | 主题分类，目录展示 |
| `tags` | ✅ 导入后 | 字符串数组，目录标签筛选用 |

### 2. 正文小节（6+1 个内容字段）

Frontmatter 之后按固定顺序书写 `## key` 小节：

```markdown
## background
投资者已签署认购文件并提交部分 KYC，AML/CDD 尚未完成……

## facts
- 认购文件已签署
- 需核对：AML 政策、基金文件接纳条款

## questions
1. 能否进入接纳流程？
2. 缺什么、谁有权决定？

## analysis
认购 ≠ 接纳。AML/CDD 未闭环前不推进接纳……

## practical_steps
1. 完成 CDD 与留痕
2. 由治理方（GP/董事会）批准接纳

## common_mistakes
- 把"签署认购"当作"已被接纳"
- Admin 自行决定接纳

## further_reading
- [AML 指引](https://…)
```

| 小节 key | 展示标题 | 内容建议 |
| --- | --- | --- |
| `background` | 案例背景 | 业务情境、主体、待办事项 |
| `facts` | 关键事实 | 已知事实、需核对的文档清单 |
| `questions` | 待决问题 | 问题列表（可有序列表） |
| `analysis` | 分析路径 | 判断链、规则与文件依据 |
| `practical_steps` | 实操步骤 | Fund Admin 落地动作（步骤列表） |
| `common_mistakes` | 常见错误 | 易错点与规避 |
| `further_reading` | 延伸阅读 | 官方指引/法规/文档链接 |

### 写作约束

1. **答案给判断路径与要点，不给编造的确定性监管数字**（费率、期限、门槛一律提示按现行官方规则复核）。
2. 小节标题必须是 `## key`（小写英文），key 集合固定；可任意用 `###` 做子标题。
3. 正文用标准 Markdown：段落、列表、表格、引用、链接、代码均可。
4. 语言：简体中文；术语保留英文原文（Cayman、CDD、PIF 等）。

## 三、导入工作流（Copilot 执行）

1. 按上文结构填充 `content/cases/Case-XXX.md`（frontmatter + 正文小节）。
2. 生成/刷新索引并本地自检：
   ```bash
   npm run gen:cases
   npm run dev   # 打开 /cases 与对应详情页核对渲染
   ```
3. 提交变更（内容 + `index.json` 一并提交）。

> 站点在构建时读取 Markdown；开发模式下编辑保存后刷新即可生效。已完成标记按 `Case-XXX` id 记录在 localStorage，`id` 变更会导致旧进度失联，故 **id 一旦分配不得修改**。

## 四、内容就绪判断

一个案例判定为"已导入（ready）"需同时满足：

- frontmatter `title` 非空；
- 至少一个正文小节存在非空内容（骨架中的 HTML 注释不计入）。

未就绪案例在目录页显示"待导入"、在详情页显示占位说明，且不可标记完成。

## 五、站点能力（V1）

| 能力 | 说明 |
| --- | --- |
| 案例目录页 | `/cases`，卡片网格，含进度统计 |
| 标签筛选 | 由已导入案例的 tags 动态生成 |
| 难度筛选 | 由已导入案例的 level 动态生成 |
| 状态筛选 | 全部 / 待导入 / 学习中 / 已完成 |
| 学习进度记录 | localStorage 记录已完成案例 id |
| 上/下一案例 | 详情页底部按编号序跳转 |
| Markdown 渲染 | 正文 `##` 小节按 card 渲染（react-markdown + remark-gfm） |
| 已完成标记 | 详情页按钮切换，目录卡片同步显示 |
